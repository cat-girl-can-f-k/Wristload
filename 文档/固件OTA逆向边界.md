# 固件 OTA 逆向边界

本文记录小米运动健康固件升级流程中已经得到源码或样本支持的事实，以及当前实现必须遵守的安全边界。它不是刷写教程，也不代表项目已经具备固件传输能力。

## 已确认事实

- V2 L2 通道编号中，PB 为 `1`、Mass 为 `2`、OTA 为 `6`。OTA 是独立通道，不能把固件包当作表盘或快应用送入 Mass 通道。
- 官方接口形态为 `updateFwUpgrade(boolean, int, HashMap<FwType, String>, String, IFirmwareProgressCallback)`。固件以 `FwType -> 文件路径` 映射进入升级流程，而不是单个普通文件任务。
- 官方回调至少区分固件类型的开始、进度和停止，并具有完成、错误、取消等状态。因此升级是多文件或多分区的独立状态机。
- 固件文件不能仅凭扩展名判断。现有 `.zip` 样本和扩展名为 `.bin` 的样本都以 ZIP 魔数 `PK` 开头。
- 已见两类清单：`ota.json` 与 `ota.sh`。`ota.json` 包含目标标识、软件版本、固件类型、分区文件路径和 MD5；`ota.sh` 描述多个分区镜像的设备端写入顺序。
- 部分正式包包含 `META-INF/MANIFEST.MF`、`CERT.SF`、`CERT.RSA`。发现这些条目只表示包中带有签名材料，不等于本项目已经验证签名链或确认其可信。

## 当前只读能力边界

固件入口在协议取证完成前只能执行本地检查：

- 验证文件实际为 ZIP 容器，并限制条目数量、清单大小和总展开大小。
- 识别 `ota.json` 或 `ota.sh`、分区镜像、目标标识、版本和固件类型。
- 校验 `ota.json` 引用的 `location_path` 是否存在于包内。
- 报告签名文件是否存在，但不得显示“签名已验证”。
- 检查结果必须明确说明没有向设备发送数据。

## 尚未确认的协议

以下信息缺少同型号设备与对应官方固件升级过程的 HCI/RFCOMM 抓包证据：

- OTA channel 6 的会话初始化与控制帧结构。
- `FwType` 的稳定数值映射及其与清单分区的对应关系。
- 分片尺寸、窗口、序号、重传、ACK 和断点恢复规则。
- 包完整性、证书链和设备侧签名校验的具体规则。
- 升级前置条件，例如电量、存储、型号、区域和版本回退限制。
- 传输结束后的校验、切换分区、重启、失败回滚和版本回读流程。

## 强制安全约束

在上述信息得到真机证据并形成可复现测试以前：

1. 不得调用现有表盘或快应用的 Mass 队列传输固件。
2. 不得仅根据 `channelOta = 6` 构造、发送或猜测 OTA 帧。
3. 不得在 UI 中使用“可安装”“可刷写”或“签名有效”等结论性表述。
4. 固件选择、解析或检查失败不得改变设备、安装队列或连接状态。
5. 后续接入必须先实现取消、超时、失败恢复与版本回读，再开放实际发送入口。

## 下一阶段取证清单

1. 对同一设备、同一固件记录官方升级前、传输中、完成后全部 HCI/RFCOMM 数据。
2. 将 channel 6 数据按 L1 序号、opCode 和方向分组，标记开始、分片、ACK、结束与重启事件。
3. 对照 `FwType` 回调日志与包内分区，建立有证据的类型映射。
4. 人为制造可恢复条件，例如取消、丢包、断连和空间不足，确认官方恢复策略。
5. 升级完成后回读固件版本，并验证设备重启和失败回滚路径。
