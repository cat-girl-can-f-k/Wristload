# 项目路线图

本文用于记录尚未完成的设备与功能，避免把“已识别型号”“实验连接”和“已验证安装”混为一谈。

## 当前优先级

1. 完成 V2 快应用安装闭环：`20/1 → Mass 0x40 → 20/2`，以设备返回的包名和结果码作为唯一成功依据。
2. 稳定 Windows 长连接、取消、超时、断链与检查点恢复；随后用 Android 真机复验同一 Dart 状态机。
3. 完成 UI、目录和安全审计，不保留无调用入口或会误导用户的实验代码。

## 经典设备（近期）

UI 的“经典设备（实验）”模式用于以下设备：

| 设备 | 已确认内部代号 | 当前状态 |
|---|---|---|
| 小米手环 7 Pro | `hqbd3.watch.l67` | Huami/Zepp 独立协议；只做安全枚举 |
| 小米手环 8 Pro | `lchz.watch.m67` | 可做安全 GATT 枚举；安装未开放 |
| REDMI Watch 4 | `lchz.watch.n65` | 可做安全 GATT 枚举；安装未开放 |

运动健康的分支证据表明，手环 8/8 Pro 固件版本以 `0` 开头时使用旧 Vela `BleTaskQueueV1`：proto、mass、voice、OTA 等为独立 GATT 特征，帧为旧 Mili 分段格式，加密使用 V1 AES-CTR。它不能复用手环 9+ 的 RFCOMM L1/L2 写入实现。经典模式在完整 HCI 证据前只读服务与版本，不发送猜测性安装帧。

小米手环 7 Pro 不能归入上述 Vela V1：运动健康将 `Xiaomi Smart Band 7 Pro` 单列为 `TYPE_HUAMI`，走 Huami/Zepp 集成；表盘工具对 7 Pro 的主要做法是替换运动健康的表盘缓存后再由官方 App 同步，而 8 Pro 具有独立的 `MI_BAND_8_Pro`/经典连接入口。两者必须使用独立适配器和独立测试证据。

表盘自定义工具只用于核对设备名、内部代号和连接入口差异；项目不会复制其代码块。已核对映射：`L67`、`M67`、`N65` 分别对应上述三类设备，但代号相邻不代表协议相同。

## 后续设备

- 小米手环 7（Zepp OS）：单独实现 Zepp 协议适配器，不放入 Vela V1/V2 分支。
- 小米手环 8：内部代号 `miwear.watch.m66`，计划在 V1 传输稳定后适配。
- Sport 名称不再触发自动断开；仍需按实际型号与协议代数做能力判断。

## 后续功能

- 设备 Debug：从运动健康 Debug 页面逐项建立命令清单，只开放有请求/响应证据且不会改写敏感设备状态的功能；危险操作单独确认。
- 网络桥接：V2 L2 已观察到 network channel `7`。实现时必须限制协议、目标地址与响应大小，默认阻止本机、局域网、回环和链路本地地址，防止设备请求被用作 SSRF/内网代理。
- 录音同步：优先研究 voice/MASS_VOICE 通道与文件元数据、校验和、断点语义，不将原始录音写入日志。
- 音乐同步：在取得文件清单、容量查询、传输完成事件和删除语义后实现；与普通 Mass 文件共享限流和恢复框架，但使用独立业务状态机。

所有新增功能都必须满足：authkey 会话有效、设备能力明确、命令结构有静态与真机证据、失败时不盲目重发。
