# 项目结构与协议证据

更新日期：2026-08-10。本文以当前工作树、反编译方法体和真机日志为准，说明代码
如何从界面一路落到 RFCOMM，以及每个私有协议结论由什么证据支撑。

## 1. 工作区边界

工作区不是单一源码仓库，而是四类材料的集合：

| 位置 | 职责 | 是否进入产品构建 |
|---|---|---|
| 当前 Git 仓库根目录 | Wristload Flutter 应用、平台插件、测试与产品文档 | 是 |
| `研究资料/协议分析/` | 逆向结论、HCI/日志分析与真机验证记录 | 否 |
| `研究资料/原始日志/` | HCI、官方 App 日志及解析脚本 | 否 |
| `私有资料/` | APK、固件、JADX、反编译源码和开发工具 | 否，禁止打包 |
| `发布包/` | Windows 可运行目录和压缩包 | 构建输出 |
| `历史归档/` | 旧版 Windows 构建 | 否 |

实际 Git 仓库即当前源码目录。外层研究和私有材料用于证明协议，不得
通过资源声明、复制步骤或构建脚本进入应用。

## 2. 技术栈与运行边界

- UI 和业务状态机：Flutter / Dart，Material 3。
- Windows BLE：`bluetooth_low_energy` 6.2.1，加本地覆盖的
  `plugins/bluetooth_low_energy_windows/`。覆盖版增加 WinRT RFCOMM、配对和数据回调。
- Android RFCOMM：原生 Kotlin `BluetoothSocket`，通过 MethodChannel 接入相同 Dart 状态机。
- 数据格式：独立编写的最小 protobuf wire 编解码、L1/L2 帧、Mass 分片。
- 密码原语：`crypto` 提供 HMAC/HKDF 组成，`pointycastle` 提供 AES-CCM 与 AES-CTR。
- 本地文件：`archive` 限制性读取 ZIP/RPK，`path_provider` 保存非敏感设置和检查点。
- 密钥存储：Windows DPAPI；Android Keystore AES-GCM。authkey 不写日志或普通 JSON。

Linux 后端没有 RFCOMM 实现，因此不宣称支持真实安装。经典设备实验模式只枚举服务，
不会进入 V2 安装状态机。

## 3. 源码分层

### 3.1 入口与界面

`lib/main.dart` 创建 `DeviceController`，负责首页布局、文件选择、authkey 输入和用户确认。
`lib/presentation/` 只渲染扫描结果、会话状态、安装任务和离线 HCI 解码结果。UI 不直接
写 GATT 或 RFCOMM。

### 3.2 应用层

`lib/application/device_controller.dart` 是当前核心编排器，包含：

- BLE 扫描、型号识别和现代/经典模式隔离；
- Windows V2 的 RFCOMM 快速连接与其他平台的 GATT 版本探测；
- L1START、f=26/f=27 鉴权、会话密钥生命周期和断链处理；
- 表盘/RPK 预安装、MassPrepare、滑动窗口发送、累计 ACK 与最终业务结果；
- 取消、超时、未知状态、检查点和从头重试。

该文件约 1,600 行，是最主要的复杂度集中点。后续若继续扩展协议，应按“连接会话”、
“业务请求”和“Mass 发送器”拆分，而不是让 UI 或平台插件承接业务状态。

### 3.3 领域层

| 文件 | 职责 |
|---|---|
| `device_profile.dart` | 广播名到型号、协议代际和表盘分辨率的映射 |
| `install_metadata_reader.dart` | 在 isolate 中读取表盘/RPK 元数据并执行 ZIP 安全边界检查 |
| `install_models.dart` / `install_task.dart` | 安装输入、检查点与 UI 状态模型 |
| `verification_gate.dart` | 私有安装帧的集中真机验证开关 |
| `install_checkpoint_store.dart` | 原子保存单一非敏感恢复检查点 |
| `transfer_settings_store.dart` | 保存发送间隔和实验窗口大小 |

### 3.4 协议层

| 文件 | 职责 | 关键证据 |
|---|---|---|
| `proto_wire.dart` | varint、length-delimited、fixed32 | protobuf nano 序列化方法体 |
| `spp_protocol.dart` | SPP 版本帧、L1 CMD/DATA/ACK、CRC16 | `TransportL1` 方法体和 n67cn 日志 |
| `auth_handshake.dart` | f=26/f=27、HKDF、双向 HMAC、确认载荷 | `WearAuthV2.java`、`o6o.java` 和真机鉴权日志 |
| `session_cipher.dart` | 鉴权后 V2 业务帧 AES-CTR | `CipherApiCall.encryptDataV2` 与 `k2.java` |
| `zau.dart` | 表盘、RPK、Mass 控制 protobuf | `zau/a9u/v8s/o1h` 方法体 |
| `mass_transfer.dart` | 22B 头、10 MiB 块、4B 片头和 CRC32 | `MassDataDispatcher`、官方日志和 HCI 原始包 |
| `hci_decoder.dart` | 离线重组 btsnoop/RFCOMM/L1 并识别会话 | 本项目辅助取证工具 |

### 3.5 平台层

`lib/platform/ble_transport.dart` 是 Dart 与平台蓝牙之间的唯一边界。Windows 的本地插件
位于 `plugins/bluetooth_low_energy_windows/windows/`，Android 实现在
`android/app/src/main/kotlin/.../MainActivity.kt`。`auth_key_store.dart` 仅定义跨平台安全存储
通道；真实加密落在各平台原生实现。

## 4. 连接与鉴权调用链

```text
扫描设备
  -> DeviceProfile 按广播名识别型号和协议代际
  -> V2 Windows: 系统配对/RFCOMM（跳过易受缓存影响的临时 GATT）
  -> 其他平台: GATT fe95 读取版本后建立 RFCOMM
  -> L1START_REQ / L1START_RSP
  -> 明文 L2 PB: f=26 sendAppVerify
  -> HKDF-SHA256 派生 DeviceKey/AppKey/DeviceIV/AppIV
  -> HMAC 校验设备签名
  -> 明文 L2 PB: f=27 sendAppConfirm
  -> 设备 confirm success
  -> sessionReady=true，业务通道启用
```

这里有两种不同的 AES 用法，不能混为一谈：

1. f=27 内的 companion device info 使用 `o6o.d`，即 AES-CCM，12 字节 nonce 为
   `AppIV(4B) + 0 + 0`，MAC 为 32 bit。证据是 `o6o.f/g` 构造 `yr3` CCM，并将末尾
   4 字节标签附在密文后。
2. 鉴权完成后的 V2 业务 protobuf 使用 `CipherApiCall.encryptDataV2`，即
   `AES/CTR/NoPadding(key=AppKey, IV=AppKey)`；入站使用 DeviceKey。

系统 Bluetooth bonding 只保护链路，authkey 才证明当前客户端持有设备既有绑定密钥。
本项目不生成账户绑定材料，也不模拟小米服务器绑定。

## 5. 安装调用链

共同前置条件是：型号属于 V2、RFCOMM 会话已通过 authkey、`VerificationGate` 已开放、
源文件在发送前重新核对大小/MD5/SHA-256。

### 5.1 表盘

```text
读取 resource.bin 的数值 faceId 和分辨率
  -> zau 4/4 预安装
  -> zau 22/0 MassPrepare，dataType=0x10
  -> L2 channel=2/opCode=1 发送 Mass 分片
  -> 等待 zau 4/5，code 只能是 2 或 3
  -> zau 4/1 setFace(faceId)
  -> 成功
```

### 5.2 快应用

```text
从全部候选 manifest 读取唯一包名和版本
  -> zau 20/1 预安装
  -> zau 22/0 MassPrepare，dataType=0x40
  -> L2 channel=2/opCode=1 发送 Mass 分片
  -> 等待 zau 20/2
  -> 结果码为 0，且设备返回包名与当前任务完全相同
  -> 成功
```

控制 protobuf 使用 `channel=1/opCode=2` 的 AES-CTR 密文；Mass 正文使用
`channel=2/opCode=1` 明文协议载荷。L1 ACK 是滑动窗口的累计确认。Mass 数据全部被 ACK
只表示文件传输完成，不能代替 4/5 或 20/2 的业务终态。

## 6. 恢复与失败语义

- 本地取消只停止发送队列，不发送尚未验证的设备取消命令。
- ACK 超时、业务超时、畸形响应或 RFCOMM EOF 都使会话失效，任务进入“设备状态未知”。
- 检查点保存路径、大小、MD5、SHA-256、业务元数据、阶段和最后确认片，不保存文件副本或密钥。
- 重连后必须重新鉴权并重新 MassPrepare；续传偏移只信任设备响应。
- 明确的设备失败会清理检查点；无法验证的终态保留检查点供人工检查。

## 7. 设备范围

- V2 Vela：手环 9/9 Pro 及已识别的新一代型号，走当前 RFCOMM L1/L2 状态机。
- 小米手环 8 Pro：旧 Vela V1，需要独立 GATT/Mili 分帧和 V1 加密实现。
- 小米手环 7 Pro：Huami/Zepp 协议，不属于 Vela V1/V2。
- REDMI Watch 4：协议代际仍未由方法链与真机 HCI 共同确认。

后三类设备当前只能在经典实验模式中做只读枚举，不得进入 V2 安装路径。

## 8. 逆向材料索引

主要反编译证据位于 `私有资料/逆向工具/`：

- `out_classes3/.../WearAuthV2.java`：f=26/f=27、密钥切片、签名顺序和设备确认；
- `out_c2/.../o6o.java`：HKDF、AES-CCM 和随机数原语；
- `out_classes3/.../CipherApiCall.java` 与 `out_classes9/.../k2.java`：V2 业务 AES-CTR；
- `out_classes3/.../TaskQueueV2.java`：业务类型到 L2 channel/opCode 的映射；
- `out_classes10/` 中的表盘、RPK 和 Mass 类：控制命令与文件分片；
- `gb_xiaomi/`：仅作独立开源实现交叉验证，不能替代官方方法体和真机证据。

证据可信度顺序为：真机 HCI 原始帧 > 官方方法体和运行日志交叉印证 > 单一静态方法体 >
第三方开源实现 > 类名/常量推断。较低等级证据不能单独解除真实发送门控。

## 9. 构建与交付

项目使用 Flutter 3.44.8 / Dart 3.12.2。Windows 测试版必须通过：

1. `dart analyze`；
2. `flutter test`；
3. `flutter build windows --debug`；
4. 检查 EXE、`flutter_windows.dll`、插件 DLL 与 `data/flutter_assets` 同批生成；
5. 启动进程并确认窗口未立即退出；
6. 将完整运行目录打包，而不是只复制 EXE。

仓库内的 `tool/build_windows_test.ps1` 固化了上述门槛。默认使用
`C:\src\flutter`，将带时间戳的完整目录、ZIP、`build-manifest.json` 和 ZIP 的
SHA-256 文件写到外层 `发布包/`：

```powershell
& .\tool\build_windows_test.ps1
```

脚本会拒绝覆盖同名产物，并分别检查 EXE、插件 DLL 与 `kernel_blob.bin` 不早于其
对应的最新输入源码，从而避免把残留的旧构建当成当前测试版，同时兼容合法的增量构建。

真机表盘/RPK 安装仍是单独的设备验收项；桌面冒烟测试只能证明程序可启动，不能证明某个
型号的私有协议安装闭环。
